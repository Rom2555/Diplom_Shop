# Дипломный проект: Backend для автоматизации закупок

REST API сервис для заказа товаров в розничных сетях.
Пользователи делают закупки по каталогу от нескольких поставщиков, при этом товары из разных магазинов можно добавить в один заказ.  
Взаимодействие с приложением ведётся только через API (фронтенда нет).

---

## Используемые технологии

**Backend** - Python 3.12, Django 6.0.6, Django REST Framework

**Базы данных** - PostgreSQL, Redis

**Инфраструктура** - Nginx, Gunicorn

**Аутентификация** - JWT (SimpleJWT)

**Документация** - drf-spectacular / Swagger

**Импорт данных** - YAML прайс-листы

---

##  Запуск проекта

1. Клонировать репозиторий:
   ```bash
   git clone <repository_url>
   cd Diplom_Shop
   ```

2. Создать файл `.env` по примеру `.env_example` (настроить почту Яндекс, `SECRET_KEY`, подключения к БД).

3. Сборка и запуск:
   ```bash
   docker-compose up -d --build
   ```

4. Миграции, сборка статики и запуск Gunicorn происходят автоматически при старте контейнера.

### Доступ к Django Admin
Для доступа к панели администратора (просмотр магазинов, заказов, таблиц БД) создайте суперпользователя:

```bash
docker-compose exec web python manage.py createsuperuser
```

При запуске система попросит ввести username, email и пароль прямо в терминале.

## Реализованный функционал

###  Пользователи

- Регистрация с обязательным подтверждением email. Токен приходит в письме, для активации его нужно отправить POST-запросом в Swagger.
- Восстановление пароля через email (также через Swagger).
- CRUD адресов доставки (контактов).

###  Товары и поставщики

- Импорт YAML: загрузка прайс-листов через Swagger (формат `multipart/form-data`).
- Архитектура ID: у разных поставщиков могут быть одинаковые ID категорий и товаров. Чтобы база данных не выдавала ошибку на дубликаты, поле `id` в моделях переименовано в `original_id`. Скрытый системный `id` используется только для внутренних связей Django.
- Управление статусом приема заказов (`/partner/state/`). Если магазин выключил прием заказов, добавить его товар в корзину нельзя (возвращается ошибка с названием магазина).
- Получение заказов поставщиком по `shop_id` (из одного заказа поставщику показываются только его товары).

###  Корзина и заказы

- Добавление/удаление товаров.
- Защита от удаления товаров, которые уже лежат в оформленных заказах.
- Оформление заказа. Атомарное списание товаров со склада.
- Отправка писем. Клиенту уходит состав и сумма, администратору - полная накладная с телефоном и адресом.
- Изменение статуса заказа с уведомлением клиента по email.

---
### Архитектура кода
- Views разбиты на логические модули: views_user.py, views_partner.py, views_orders.py.
- Логика импорта YAML-прайсов вынесена в отдельный модуль shop_app/services.py.
- Отправка писем вынесена в shop_app/mail.py.
- Подсчет суммы заказа вынесен в метод модели Order.total_sum().

##  Важные замечания

1. **`shop_id` для корзины**  
   ID магазинов можно посмотреть в Django Admin (`/admin/`). Также эти поля есть в каталоге товаров (`GET /api/v1/products/`), чтобы не приходилось входить в админку при тестировании.

2. **Работа с письмами**  
   В письмах текст говорит: "Зайдите в Swagger по такому-то адресу и отправьте такой-то JSON". Это сделано специально, так как API не имеет фронтенда.

3. **Чистая база данных**  
   В пайплайне (`deploy.yml`) прописана команда `docker-compose down -v`. Это значит, что при каждом пуше в GitHub база данных и контейнеры пересоздаются с нуля. Чтобы прогнать тест на чистой базе, можно просто сделать пустой коммит и запушить.
